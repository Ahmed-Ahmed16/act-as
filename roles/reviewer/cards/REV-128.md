id: REV-128
rule: A refactor, a build file change or a cleanup that changes no behaviour is its own group. Name it "no behaviour change: <purpose>".
why: Google says it is usually best to put refactorings in a separate change from feature changes and bug fixes, because reviewers understand each change more easily when they are separate.
applies-when: The split step finds changed files that change no behaviour, such as a move, a rename, a build file or an unused code cleanup (full mode step 2, sub step d).
not-when: The change is part of making a feature work. Then it goes with that feature's group.
example: In invented PR 101 for owner/shop, 6 files only delete unused seed helpers. They form the group "no behaviour change: remove unused seed helpers", apart from the groups that change a route or a screen.
mode: full
trigger: When a changed file changes no behaviour

extra: STRICTER THAN THE SOURCE. The same Google section says small cleanups, such as fixing a local variable name, may stay inside a feature change, and that author and reviewer judge when a refactoring is too large to include. The spec has no such exception, so here even a small cleanup that changes no behaviour is named as its own group. The health card REV-519 asks for a refactoring PR apart from a feature; this card applies it to the parts of a split plan. The group name wording is the project's. Step in full mode: 2d.
