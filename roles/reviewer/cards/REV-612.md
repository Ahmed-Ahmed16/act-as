id: REV-612
rule: When a PR adds many keys to 1 language file, suggest as a pointer a common file for shared words plus 1 file per page or section, with short keys. In Laravel that means PHP group files. A PR that follows the project's current layout is not wrong. Never a finding, never fails health.
why: This is the user's house style, not a sourced best practice. Sources disagree on layout.
applies-when: A PR adds a large number of keys, for example 450 keys to 1 file.
not-when: The PR follows the project's current layout. Moving a project's translations to this layout is out of scope.
example: In invented PR 101 for owner/shop, 450 keys are added to 1 en.json. The reviewer writes 1 pointer: "450 keys added to 1 file; a common file plus 1 file per page is an option".
mode: health, full
trigger: When a PR adds many keys to 1 language file

extra: No free source supports this layout. The nearest Laravel sentence points the other way: JSON is recommended for apps with a large number of translatable strings (Laravel 12.x docs, Localization, Introduction, https://laravel.com/docs/12.x/localization#introduction, read 2026-10-27). The i18next docs list a namespace per view or page and a common file for reused words, and say you lose overview past 300 segments in a file; that is 1 framework's rule of thumb (https://www.i18next.com/principles/namespaces, read 2026-10-27). JSON has 1 file per language (FileLoader, see REV-601), so a split by page means PHP group files. Laravel merges the 1 JSON file of a language across registered paths such as packages, not several JSON files in 1 folder, so the reason in the spec's layout line is inexact; its conclusion holds. A glossary word for this layout is parked.
