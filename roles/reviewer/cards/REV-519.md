id: REV-519
rule: Ask for a refactoring to go in a separate PR from feature changes and bug fixes.
why: Google says reviewers understand the changes of each PR more easily when a refactoring is not mixed into a feature or a fix.
applies-when: The PR mixes a refactoring (a move, a rename, a restructure with no change in behaviour) with a feature or a bug fix.
not-when: The cleanup is small, such as renaming a local variable, or the refactoring is so small that it does not make the review harder.
example: In invented PR 101 for owner/shop, a cart discount feature also moves 4 classes to a new folder and renames them. The reviewer asks the author to send the move as its own PR first.
